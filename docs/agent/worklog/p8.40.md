## p8.40 — A local-only project has no documented way to retire a track · 2026-11-03 · @Alpha-30-creator

**What changed:** *Retiring a track* no longer asks whether a worktree's commits are on a remote.
It asks whether **its own removal** would lose work, which consults no remote, so a local-only
project retires a track the same way every other project does. Three refusals, listed once in
`ws-shared/tracks.md` and pointed at by `ws-start`, `ws-ship` and `ws-fanout`: uncommitted changes;
an **operation in progress** (rebase, cherry-pick, merge, revert, bisect); and commits reachable
from **no branch, tag or remote-tracking ref**. "On no remote" became a note, as did the
worktree's reflog naming commits no ref contains, and the ignored files the removal will delete.
`ws-wrap`'s push now degrades with a named reason instead of a raw git fatal. The decision is
[ADR 0006](../../decisions/0006-retirement-refuses-what-removal-would-lose.md).

**The task's premise was false, and so were three records that repeated it.** Its `Why`, p8.32's
amendment of the same morning, and two `known-limitations.md` entries all said the refused commits
"exist nowhere else". **`git worktree remove` removes a checkout, not a branch** — measured, after
removing a worktree whose branch held an unpushed commit, `refs/heads/<branch>` still points at it.
In a remoteless repo the old test refused *every* worktree, including a fresh one with no commits
of its own. So this was never "document the way past the guard"; it was "the guard asks the wrong
question". `docs/product/overview.md` had contained the refutation all along: the same paragraph
opens with *"It never touches a branch, a commit, a pushed PR or the tracker item"* and then
justified the refusal with *"those exist nowhere else"*. Nobody had read the two sentences together.

**Decisions:**
- **The removal question refuses; the backup question notes.** *Rejected:* keeping the remote test
  as a second refusal — it reinstates the block for exactly the projects this task is about.
- **The reflog sweep reports rather than refuses.** A commit the worktree made and then stepped
  off is reachable from no ref *and* absent from the count, so the reflog is the only place it is
  named. Shipped first as a refusal; *rejected* after measurement, because a reflog holds every
  amended-away and rebased-away commit by design, so it fired on `commit --amend` and
  `pull --rebase` on every project — and `ws-ship` holds the tracker transition on the
  verification line, so such a track could not ship at all. The only remedy it offered was to
  create a branch naming a commit the author had deliberately replaced.
- **Mid-rebase became a refusal**, closing the gap p8.32 recorded as uncatchable. That record was
  right that no commit count can see it and wrong that nothing can: `rev-parse --git-path` can.
- **The three refusals are one table, not four restatements.** *Rejected:* each caller stating its
  own subset, which is how `ws-start` came to test two of three and offer tracks retirement refused.
- **Ignored files are named before the yes, not refused.** A built `dist/` going with the worktree
  is documented behaviour and an `.env` is recoverable with `ws-env pull`.
- *Rejected overall:* documenting the local bare mirror as the answer (it answers the backup
  question, which is real); `git bundle`; an acknowledgement override, which would be asked in
  three shapes that lose nothing and so train an agent to click through the one that matters.

**Evidence:** the block extracted verbatim from the shipped document — located by its own
`# ---------- inputs ----------` header, since the first `bash` fence in the file is a different
block — filled and executed across 12 fixtures, plus the three reviewers' own 14, 14 and 14. The
whole block, not the pre-check: round one's record said "retires" for cases where only the
counting half had run. Cases: the ordinary paths that must retire (`amend`+push, `pull --rebase`,
`reset --hard`), the three refusals, a stepped-off commit retiring with its note, a commit named
only by `refs/worktree/*`, a listing failure injected after the pre-check, a worktree containing a
submodule, residue in the parent, `p3.1` against `p3.10`, unborn `HEAD`, and a remote-ful repo with
a commit the mirror lacks. `scripts/check.sh` green; graph audit at its one pre-existing finding.

**Risks learned:**
- **A blanket refusal protects things it does not know about.** The old test refused everything in
  a remoteless repo, so it incidentally covered rebases, stepped-off commits and ignored files —
  none of which it could name. Replacing it with a precise test removed the accidental coverage
  along with the wrong justification, and the only way to see that is to enumerate what the
  blanket was catching. **A narrower test is better only once what it stopped catching is
  accounted for.**
- **And restoring that coverage can cost more than the loss it prevents.** Round two's finding is
  the same question asked of the fix: the signal the new refusal keyed on is produced constantly
  by the workflow this pack prescribes. Round one asked *what else was the blanket catching*;
  round two asked *what else does the replacement block*. Both have to be asked.
- **Three rounds, and each found the previous round's fix wrong in a new way.** Round one: three
  loss cases. Round two: round one's fix blocks the ordinary path, plus the callers still carrying
  the old design. Round three: the demotion missed the rationale section **of the file it edited**,
  which still called the sweep a refusal and claimed it *subsumed* a live one, and missed
  `docs/product/overview.md` — the file round two had named, while three others named beside it
  were fixed. A fix is not a sweep; the sweep has to be for the *claim*, in every file, every time.
- **Two pre-existing false `clean`s in the same block.** `wts_for` piped `git worktree list` into
  `sed`, and a pipeline exits with its last command's status, so git's `128` in a non-repo became
  `0`, the caller's failure branch never fired, and the block printed `clean: track <id> removed`
  while the worktree holding the work was still on disk — the line `ws-ship` gates the tracker
  transition on. The removal loop then took its list from `<<WT $(wts_for "$r") WT`, where command
  substitution discards the status again, so a listing failure deleted the track's plan, journal
  and evidence and left the worktree standing. The document warns about pipes masking exit status
  four bullets below the code that was doing it.
- **A verification that measured nothing and passed.** The exit-status fix was checked by reading
  `$?` of a wrapper script ending in `echo "exit=$?"` — the echo's status, always `0`. The fix was
  correct and the check was theatre. The block's status has to be read from the line it prints.
- **The tidiest spelling was the wrong one, twice.** `rev-list HEAD --not --all` counts zero
  whatever is there, because `--all` includes `HEAD`; and asking `for-each-ref --contains` *of the
  worktree* finds `refs/worktree/*` refs that are about to be deleted with it, so the sweep
  certified exactly the commit it existed to find. One `-C` apart.
