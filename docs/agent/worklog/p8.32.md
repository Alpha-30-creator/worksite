## p8.32 — A retired track leaves its parent directory behind, and the root it lives under is undefined · 2026-11-03 · @Alpha-30-creator

**What changed:** `ws-shared/tracks.md` gained *The worktree root — one definition, resolved
absolutely* — the root is now a cartridge key (`worktree_root:`) with a stated default, resolved
once per session to one absolute path — and its *Retiring a track* section was rewritten: the
no-upstream refusal became a count of commits reachable from `HEAD` and from no remote, and a new
step 4b removes the `<id>/` parent directory that `worktree remove` leaves behind. `ws-start`
records **absolute** paths in `task.md`'s `- Worktrees:` line and resolves the root before its
stale sweep; `ws-ship` and `ws-fanout` were brought onto the same rule; `ws-setup`'s template
carries the key and states where the root lands for a single-repo project, where it is necessarily
outside the workspace. Repo-side: a `worktree_root` row in the cartridge schema, the key in this
project's cartridge, and four entries in `records/known-limitations.md`.

**The task's own premise was false, and criterion 2 encoded it.** The criterion says to remove the
parent "when removing its last worktree leaves it empty". The real instance that motivated the
task — 9.6M under `<proj>-tracks/p7.4/` — is **not** empty: it holds a build-output tree with no
`.git`. `rmdir`, which is what the criterion prescribes, would have reported success on the one
case the task was filed for. What shipped instead searches for the parent two independent ways,
removes it when it holds no files, and otherwise prints its size, lists what is inside and
**deletes nothing**.

**Decisions:**
- **Resolution refuses rather than guesses.** `/`, `~`, `~/`, `.`, `..`, trailing slashes, and a
  workspace root directly under `/` are each a refusal with a reason. *Rejected:* normalising a
  doubtful value into something plausible — a resolver that always answers is how one project got
  two roots with half its tracks in each.
- **`cd -P` / `pwd -P` everywhere, and the root canonicalised whole.** *Rejected:* canonicalising
  only the parent — a symlink in the last segment is then still unresolved, and `cd`/`pwd` are
  logical by default, so a symlinked workspace path resolved to a different root than the real
  path did. Measured, in the code written to prevent exactly that.
- **The verification line reads step 4b's own result.** *Rejected:* letting it compute its own
  answer from `$wt_root/$id`, which is what the first draft did — see below.
- **A non-empty parent is reported, never cleared.** *Rejected:* `rm -rf` on it. Retirement removes
  session state; 9.6M of someone's build output is not session state, and the one case the task
  exists for is the case where the two are indistinguishable from inside the loop.
- **An existing root under the other reading of `../` is reported, not adopted.** It prints both
  paths and what the other holds, and offers the cartridge key or a move — "not both at once".

**Evidence:** nine fixture cases in the track's `verify/fixture-runs.md`, each run with the shell
block **extracted verbatim from the shipped document** rather than retyped, so the thing tested is
the thing shipped: happy path with no upstream; a commit on no remote; residue under the other
reading; nested `.DS_Store`; a real checkout at depth 2; a vendored `.git` with files beside it; an
empty directory tree; `worktrees: false` leaving an unused root alone; and the single-repo layout.
Plus `p3.1` proved not to match `p3.10`, seven resolution rows from two different working
directories, and a read-only pass over the real 9.6M instance confirming the default resolution
lands on it and 4b reports it. `bash scripts/check.sh` green; `ws-refine`'s graph audit at one
finding, verified pre-existing in a skill this task did not touch.

**Risks learned:**
- **Two answers to one question, and the reassuring one printed last.** Step 4b correctly reported
  `LEFT: … still holds a git checkout`, and the verification line four steps later printed
  `clean: track p8.32 removed` — because it recomputed the answer from `$wt_root/$id` instead of
  reading what 4b found. The p8.24 defect class, reproduced inside the fix for a different one.
  They now share one variable, so a reported `LEFT` **is** a `NOT REMOVED`: the same fact, not two
  agreeing computations.
- **A line added to tidy input defeated the section's central guarantee.** Stripping trailing
  slashes before validating emptied the string for `worktree_root: /`; `dirname ""` is `.`; the
  root became **the caller's working directory**. Measured as `/private/etc/` from `/etc` and as
  the repo path from the repo — cwd-dependence introduced by the one section whose entire purpose
  is cwd-independence. Validation now runs before anything strips.
- **The sentence most likely to be false is the one replacing a sentence just proved false.** Round
  one correctly refuted a claim about a local upstream satisfying the guard. The replacement I
  wrote — that for a remoteless project the guard is now "an absolute bar", "exactly impossible to
  satisfy" — went into `known-limitations.md`, into p8.40's amendment **and into p8.40's title**,
  and is also false: two commits on no remote, `git push` to a `--bare` repo on the same disk,
  count `0`. A local mirror satisfies it with no network and no hosting, and unlike the old
  upstream trick it satisfies the guard's *meaning*, because the commits really are in a second
  place. `README.md` had said all along that the workaround is merely undocumented; it was right,
  and the two records I "corrected" were the wrong ones. Five more instances of this pattern on
  this project today, seventeen in all.
- **A final draft nobody re-read.** Two paste sites in this task's own new prose were physically
  mangled — an enumeration that lost its content under a sentence counting five states, a
  parenthetical spliced into the middle of another sentence — in the bullet list that is the
  section's reference text for the next agent. The edits were scripted and the result was never
  looked at.
- **Two gaps recorded rather than closed**, both in `records/known-limitations.md`: the retirement
  block's fenced shell is **never executed by `verify` on any platform**, so GNU `find -delete` on
  a `..`-bearing path stays untested (there is no GNU `find` on this machine); and mid-rebase or
  mid-bisect state is invisible to every check retirement makes, so `worktree remove` discards it.
