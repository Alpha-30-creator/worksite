## p8.10 — Cleanup exists on exactly one path, and nothing ever sweeps · 2026-11-01 · @Alpha-30-creator

**What changed:** track retirement is now defined once, in `ws-shared/tracks.md`, as a single
guarded block that four skills point at. `ws-ship` resolves an explicit track id, splits Harvest /
Retire / Mark done, and will not mark a task done until removal has printed a verified line.
`ws-fanout` passes the id per track and reconciles an abandoned batch. `ws-start` gained a stale
sweep that reports orphaned track directories and worktrees and asks. `ws-task` retires a dropped
track after harvesting a three-line stub.

**Decisions:** the rule was never missing — `ws-ship` already removed the track directory, the
journal mirror and the worktree. Five reasons it never ran were the defect. The retirement
sequence is written in **one** place because four copies drift.

*Rejected: moving cleanup earlier in `ws-ship`.* Verified against the file: harvest was already
section 5 and mark-done section 6, so ordering was never the problem, and deleting the plan and
journal before the merge lands would destroy the cold-resume path.

*Rejected: a fifth tracker-adapter question (`status <id>`) for the sweep.* Unnecessary — every
adapter's existing list already answers it well enough, and the sweep only ever asks. Filed as
p8.12 instead.

*Rejected: a show-and-wait carve-out for `ws-ship` on the happy path.* The build added one,
reasoning that the user had already said ship and that a final prompt is where sessions die with
the track still on disk. **The user decided it asks.** The reasoning pointed the wrong way: a
track left on disk is visible and recoverable, and this task's own sweep now finds it; state
deleted without an answer is neither.

**Evidence:** two review rounds. The first found **five Must-fix** issues, the worst being an
unguarded `rm -rf "$state_dir/tracks/$id"` that with an empty id would have deleted **every track
on the machine** — in a change whose purpose was safe cleanup. Its root cause was a single false
sentence in the task brief ("cleanup has no id to substitute, so it silently removes nothing"),
which is why nobody wrote the guard: nobody guards a no-op.

Verified by **execution**, not reading: empty id → refuses, nothing touched, all four fixture
tracks intact; unset id → aborts under `set -u`; real id → removes only its own track, leaving
`p3.10` and `other` alone. The guard, the one-fence composition, the non-suppressed upstream
check, and the `while IFS= read -r` loops were each exercised against a fixture whose path
contained a space. `ws-refine`'s graph audit clean; 5/5 changed skills confirmed on each of three
agents; library and repo copy identical.

**Risks learned:** the pack's recurring shape — **a rule that exists with no path that executes
it** — now has seven instances, one of them inside the fix for that very pattern (a no-upstream
refusal that could not fire because `2>/dev/null` ate its only signal). Two bugs in this task
reported **false success**, which is worse than crashing: a `grep -F` suggestion of mine that
missed the single-repo layout, and a word-splitting loop that printed `clean` while a worktree
remained. Both were found by running the code, neither by reading it.

**Docs touched:** `docs/roadmap/P8-pack.md`, `docs/STATUS.md`, and the five library skills.
Follow-ups filed: p8.11 (`ws-wrap` says nothing about the id), p8.12 (adapters cannot answer
`status <id>`), p8.13 (`for r in <repos>` survives in three skills, one of which warns against
it). One edge case noted but not filed: the new no-upstream refusal fires on a branch already
merged into the integration branch, where the commits are in fact safe.

**PRs:** none. Merged locally as `c57380a`; history was later rewritten to purge an unrelated
leak, so the commits carry new hashes.
