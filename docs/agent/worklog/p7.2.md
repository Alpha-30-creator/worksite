## p7.2 — Tag and announce · 2026-11-03 · Alpha-30-creator

**What changed:** the README's claims were enumerated and checked one at a time against the tree
`v0.1.0` was cut from. **One was false**: the "Status: what works and what does not" table still
named p7.1 — "no stranger has run the loop end to end from these instructions" — and p7.1 shipped
on 2026-11-02. The row is replaced by the gaps a reader would actually hit (p8.39, p8.40, p8.30)
and by what the stranger run produced. The enumeration became
`scripts/check-readme-claims.sh`, which reads every quantity out of `README.md` and compares it to
the tree, exits non-zero, and was run against the tagged tree extracted with `git archive` into an
empty directory: 39 ok, 0 failures. `v0.1.0` is tagged and pushed; the release text is drafted and
deliberately not published.

**Decisions:**
- *Rejected: deleting the gap table.* An empty "what does not work" section reads as "everything
  works", which is a worse claim than a stale one.
- *Rejected: listing all open tasks in it.* The table is reader-facing; four of the seven are this
  repo's own authoring and tooling, and the README says so in one line with the board linked.
- *Rejected: keeping the enumeration as track-only evidence.* It would be deleted at retirement and
  the next tag would re-derive it by hand — the shape p8.36's harvest had just finished describing.
- *Rejected: folding the checker into `check.sh` in this PR.* That would make it a gate, and the
  review's finding is precisely that it was not fit to be one. Filed as **p7.3**.
- *Rejected: a version line in the README.* It would need editing at every tag, and the task's own
  body says the release mechanics need no tracking.
- *Deliberate:* the announcement is not published. Tagging is reversible and private in effect;
  announcing is the first public statement this repo makes, so it waits on the owner's wording.

**Evidence:** [PR #22](https://github.com/Alpha-30-creator/worksite/pull/22), merged `43d965a`;

`bash scripts/check.sh`: all six sections.

**Risks learned:**

*A verifier that holds the expected values is not a verifier.* The first version of the claim
checker compared the **tree** against numbers written inside the script, so it could not see the
claim it was checking. A reviewer mutated a copy and nine false READMEs passed, among them
"Thirteen skills" → "Twelve" and the entire `ws-plan` table cell replaced with "a shipped feature",
which it reported as a *note* at exit 0. For a task whose one criterion is "the claims all
verified", that is worse than having no checker, because it certifies. The generalisation worth
keeping: **a check must read the claim from the artefact that makes it.** The fix is directional,
not additional — one `claim()` function through which every comparison passes, reading from a
whitespace-normalised copy of the README, since three checks had silently found "no claim" on
sentences that wrap.

*The mutation test is the artefact, not the checker.* 17 for 17 is what makes the checker worth
trusting, and no amount of reading it would have produced the same confidence. A check with no
demonstration that it refuses a bad input is an assertion.

*Incrementing a count is not recounting it.* `SECURITY.md` and `CONTRIBUTING.md` said "three shell
scripts"; I added one file and wrote "four". There are **five**, so the original was already wrong
and the edit preserved the error while looking like maintenance. `SECURITY.md`'s "the only code
that ever runs is …" list also omitted the new script, which made a security statement false.
Both now derive the number, and `SECURITY.md` records how it was wrong.

*Correcting a false claim is where the next one gets written.* Three times in this task: the p8.30
gap row's first draft described a problem p8.30 is not about; the README's "each turned into a fix
or a written limitation" ignored that two of the 44 became tasks; and **my first correction of that
was itself false** — I wrote that those two tasks were the first two gap-table rows, when the
stranger run filed p8.35 and p8.36 (both since shipped) and left one *criterion* on p8.30. Group 10
of the checker now checks that sentence against p7.1's own acceptance criteria, because a claim I
have got wrong twice is exactly the claim that needs a machine on it.

*The leak guard earned its place.* `check.sh` §1 refused the checker's first draft for reaching
agent-sync's `package.json` through a hardcoded workspace path — before the commit that would have
put it in public history, which is what `AGENTS.md` asks for rather than a fix afterwards.

*And a false negative of my own.* The first grep for `INSTALL.md`'s stop-language was
case-sensitive on `STOP` and returned 0, which made a true claim look unsupported; the file stops
nine times over. A verification pass produces false negatives as readily as prose produces false
positives, and nothing but re-reading caught it.
