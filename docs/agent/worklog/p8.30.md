## p8.30 — Two skills give opposite instructions about pushing the library · 2026-11-03 · @Alpha-30-creator

**What changed:** `ws-refine` now carries one statement of the rule, under a new *Who may run what
— deploying is not publishing* section beside its Deploy step, and `ws-fanout` (five sites),
`ws-review`, `ws-shared/trackers/README.md`, this project's cartridge and ADR 0003 all point at it
instead of answering it themselves. The rule separates a **deploy** — `agent-sync apply`, local,
reversible, commits and pushes nothing, run by the lead as often as verification needs — from a
**publish** — `save`'s commit-and-push half, run by the lead once, after review. A subagent does
neither: it edits library files and stops.

**The task understated the problem in its own framing.** "Two skills" disagreeing was the smallest
part. `ws-fanout` disagreed with **itself** in three places: the owning builder "may run that
store's `publish:` command", that same command "runs once, after review", and "Commit, do not
push" three lines below the permission — while a builder runs *before* review and `save` pushes.
`ws-fanout` also never mentioned the audit at all, so in a batch nobody was told who ran it. A
fourth site was `ws-review`, which tells its reviewer that stack-pack edits go through
`agent-sync save` while running that reviewer as a background subagent by default. A fifth and
sixth were outside the pack entirely: `docs/agent/reference.md` — the cartridge `AGENTS.md` orders
every agent to read *before anything else* — and **ADR 0003 item 5, status accepted**.

**Decisions:**
- **`ws-refine` owns the rule.** It is the skill about changing the pack and already owns the
  Deploy and Audit steps. *Rejected:* `ws-fanout` owning it — the skill that merely *encounters* a
  rule would have to restate it for every other caller, which is how this got to six sites.
- **Deploy and publish are separate rows, not one step with an exception.** The two halves of
  `save` have different costs and different audiences. *Rejected:* keeping "once, after review"
  and carving out an exception for verification — a rule plus an escape hatch reads as a rule
  nobody follows.
- **ADR 0003 amended rather than contradicted.** Its item 5 said `publish:` is forbidden "in every
  *other* brief", which left the owner holding the command. Narrowing an accepted decision in
  silence is how the pack ends up with two rules again, so the header says `item 5 amended
  2026-11-03 (p8.30)` and the item carries the reasoning.
- **"Lead" is defined by a test, not a role**: the session that can wait for a yes. A `ws-fanout`
  lead that is itself someone's subagent is a subagent for this rule.

**Evidence:** six artefacts in the track's `verify/`. The rule and every pointer, with the four
searches that would find a second grant of permission all returning nothing; the audit gate
measured firing (one undeployed library edit → three abort lines, exit 1 → `apply` → exit 0); the
five `ws-fanout` sites before and after; the adapter mechanism; the graph audit at exit 0 with
links 9 → 12 and 0 broken; and the two repo-side sites with their before and after.

**Risks learned:**
- **The rule's first draft was unsatisfiable for exactly the changes the skill exists to make.**
  It said the lead runs `save` "once, after review" — but `ws-refine`'s own *Verify in two runs,
  and the first one must fail* requires invoking a skill before deploying and again after, and
  verification precedes review in this pack's loop. A skill-body change therefore **must** be
  deployed before review. The proof that this was not theoretical: **this very change was deployed
  to all three agents before its own review ran**, because it had to be. A rule that the work
  producing it could not follow is a rule with a hole, and the hole was invisible from inside the
  section — it took a reader who went looking at what the rest of the file requires.
- **Two false statements, written while fixing a false statement**, both inside the one new
  section, both caught by review. "`agent-sync save` is the only thing that bridges them" —
  `apply` bridges with no commit and no push, and **my own table row three files away forbids a
  subagent "no `apply`, no `save`" as two distinct deploys**, so the change already contained the
  contradiction. And "an adapter written only into one deployed copy is overwritten by the next
  deploy" — the next deploy **stops and asks** whether to adopt it into the library or overwrite
  it, which I had watched `agent-sync` do earlier the same day on unrelated skills. Twelfth and
  thirteenth instances of this pattern on this project.
- **A rule stated in the pack cannot fix a contradiction stated outside it.** Four of the six
  sites were pack files and two were not: the project cartridge and an accepted ADR. The cartridge
  is the file with the *highest* read priority in the project and it was the one still giving the
  retired answer. When a change narrows a rule, the sweep has to include the records that stated
  the old one, not only the skills that execute it.
- **An attribution that reads better than it is true.** The first draft said "a stranger following
  `INSTALL.md` wrote a correct `pitwall` adapter". The record it cites says the strangers were
  *two briefed agents* and explicitly calls that "the one place this is **not** a true stranger
  run", and the name `pitwall` appears nowhere in the repo. In a public pack "a stranger" reads as
  a third-party user. Corrected to what the record says.

**Docs touched:** the library's `ws-refine`, `ws-fanout`, `ws-review`, `ws-shared/trackers/README`;
and in this repo `docs/agent/reference.md`, `docs/decisions/0003-…`, `docs/records/known-limitations.md`.
