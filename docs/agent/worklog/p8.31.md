## p8.31 — The leak surface has three uncovered edges and nothing asserts any of them · 2026-11-02 · @Alpha-30-creator

**What changed:** `scripts/check.sh` section 1 now strips the allowlisted substring out of each
line instead of discarding the whole line, so a private name sharing a line with the public npm
scope is caught; the allowlist moved into `scripts/leak-patterns.txt` as `!` data, making that
file the sole definition of coverage. Section 2 asserts that `ws-shared` is the only skill
carrying `disable-model-invocation: true` — the arithmetic three documents' skill counts rest on.
Two new sections: 5 asserts `state_dir` is matched by a git ignore rule, 6 reads the unreachable
objects in `.git/objects` and fails on any pattern hit not declared in the new
`scripts/object-store-baseline.txt`. In the library, the journal entry header carries a derived
device alias rather than the device name, and `ws-start` asserts the ignore rule for projects
whose own `verify` does not.

**Decisions:**
- **Sections appended, not inserted.** Numbering 5 and 6 rather than renumbering keeps every
  existing "section 1" citation in the docs true. *Rejected:* putting the ignore assertion early
  because it is cheap — within one run the order does not matter, and the citations do.
- **The allowlist is declared data, not a literal.** *Rejected:* narrowing the inline string to
  `@abdur-codes/`. It shrinks the hole without closing it — a line carrying the scope and a
  private name still passes. The criterion said so and the measurement agreed.
- **The object-store residue is declared, not pruned.** *Rejected:* `git gc --prune=now`, which
  is the obvious remedy and the wrong one: this workspace's object store is shared with live
  worktrees whose unreachable objects are wanted. *Rejected:* making section 6 a separate opt-in
  script, which would leave nothing asserting it routinely. *Rejected:* suppressing the hashes
  silently; the baseline file carries the measurement and the reason, so a hash that is not in it
  fails.
- **The device alias is derived, not configured.** `dev-` plus six hex of `sha256(device)`, with
  an optional override in the state dir and a `dev-unknown` fallback. *Rejected:* a
  `device_alias:` key in `device.yaml` — that file is agent-sync's schema, so the fix would need
  an upstream change and a value nobody has set. Deriving needs neither and is safe by default.
  *Rejected:* reading `hostname`, which is the very string that tends to carry the owner's name.
- **No ADR and no dated record.** Nothing here chooses between alternatives at the level
  0001–0004 do, and the pruning decision is a dated measurement, so it lives in the baseline file
  and the purge runbook. *Rejected:* a `docs/records/` page duplicating the baseline's own
  measurement.
- **Synthetic fixtures.** Every negative fixture used a `zzprobe` pattern rather than a real
  private name, so the evidence is committable — p1.2's was not, and had to be enumerated in
  prose instead.

**What review caught, and it was the important half of this task.** The first commit shipped two
**fail-open** silent passes in the leak guard itself, and both were mine:

- **The allowlist filter passed its list through `awk -v`, and BSD awk rejects a literal newline
  there.** A *second* `!` entry in the pattern file made the filter emit nothing, so `grep` saw
  empty input and section 1 printed `ok` on a real leak — triggered by using the pattern file
  exactly as the header comment I had just written invites. The fix that moved the allowlist into
  the file to make coverage auditable had made the file unsafe to extend. Fixed with `ENVIRON`,
  which also stops `awk -v` expanding escape sequences in an entry.
- **Section 6 tested each object with `grep -q`.** `grep -q` exits on the first match and closes
  the pipe; `awk` upstream then dies of SIGPIPE and, under `pipefail`, the pipeline status is 141
  — so the `|| continue` skipped the hit. A 2.6MB unreachable blob with its match on **line 1**
  was passed over silently while still being counted as scanned. The small blobs in this store
  are why it looked like it worked. Fixed with `grep -c`, plus a `git cat-file -e` probe so an
  object that cannot be read fails the section instead of reading as clean.

Two more of substance:

- **An unmet criterion with a live path.** `ws-wrap` is the only skill that writes a journal entry
  from its own inline template rather than from `tracks.md`, and it still wrote the raw
  `<device>` into the entry it then mirrors **and pushes**. Changing `tracks.md` alone could not
  reach it. The criterion said "or through any other path" and meant it.
- **My own comment was false.** Section 6 claimed "two independent counts of the same set" when
  both derive from one `git fsck`. The honest fix was to correct the comment to what the check
  actually catches, rather than to invent an independent count so the sentence became true. A
  real tightening came with it: any non-zero `fsck` exit now fails the section, since `fsck`
  exits 0 when it merely finds unreachable objects.

And **five documentation statements the first commit invalidated and left standing** — including
`SECURITY.md` saying the allowlist was inline four lines above the paragraph dating its removal,
and `CONTRIBUTING.md` still enumerating four sections. The project's own risk list warns about
exactly this ("treat a number appearing twice in one file as a claim about arithmetic") and it
happened anyway, in the commit that corrected a different count.

**One finding did not reproduce, and it was the most alarming one.** The review held that a blob
left by a refused commit is `dangling` rather than `unreachable`, so section 6 could not see its
headline case. Measured four ways: with `--unreachable`, git reports `unreachable blob` for both
`git hash-object -w` and `git add`-then-`reset`; `dangling` appears only *without* the flag. Its
second half was valid and was fixed — section 6 read blobs only, against a criterion saying "no
unreachable **object**", and now scans tree filenames too. A tree whose only private string was
the path `src/<name>/`, with clean file content, was invisible before.

**Risks learned:** three, all of the project's recurring shape — a check that is green only where
it was written.
- **`git check-ignore` on a directory-only rule needs the trailing slash.** A rule written
  `.worksite/` matches directories only, and git can tell a bare path is a directory only by
  looking at the filesystem. `git check-ignore -q .worksite` therefore answers "ignored" on a
  checkout where the directory already exists and "not ignored" on every fresh clone and in CI.
  Measured both ways. The obvious form would have passed here and failed everywhere else.
- **A local `git clone` hardlinks the whole object store, unreachable objects included.** The
  fixture for section 6 had to be cloned over `file://` to start from zero; a `--local` clone
  would have handed the fixture the very residue the section measures.
- **A reflog keeps an abandoned commit reachable, so section 6 cannot see its residue until the
  reflog expires** — typically 90 days. The section is at its weakest in the minutes after the
  mistake it would catch. Measured: an abandoned commit's tree appeared to it only after
  `git reflog expire --expire=now --all`. Recorded in `known-limitations.md`.

**The guard refused this very entry, which is the shortest possible proof that it works.** The
first draft of the row above wrote the allowlisted string out in full as part of the command it
was describing. Section 1 failed the working tree before the commit, naming the file and the
line — so the harvest documenting the leak guard was stopped by the leak guard, and nothing
dirty reached history. The rule that makes that possible is `docs/agent/worklog/` not being in
`excluded()`; p1.2 relied on the same property for `docs/records/`.

**Then section 6 caught the blob that refusal had left behind — its own motivating case, live,
within a minute of being written.** `git add` had already written the bad draft into the object
store before section 1 refused the commit, so the next run reported one undeclared unreachable
blob. Identified by hash: 12582 bytes, first line the heading of this entry, line 52 the one with
the name in it. Loose, in no reflog, not in the index, no stashes, nothing referencing it.

It was removed by deleting that one loose object file by exact path — the p1.2 precedent, and
**not** `git gc --prune=now`, which the baseline file forbids here because this store is shared
with live worktrees. `git fsck` reported no errors afterwards and section 6 went back to three
declared, zero undeclared. The whole sequence — guard refuses, residue remains, section 6 names
it, one object removed by hash — is the argument for the section, and it ran on its author by
accident.

**Found, recorded, not fixed here:**
- **`ws-refine`'s own audit block cannot be run as delivered.** It contains four `$0` references
  inside fenced awk programs, and the delivered copy of a skill has the caller's argument
  substituted into them, so part 3b's scanner dies and the part reports zero findings having
  scanned nothing — the exact silent-pass shape p8.24 exists to catch, inside the file that
  catches it. p8.35's part 3b excludes `$0` deliberately, so the audit cannot see this about
  itself. Worked around by running the audit from the library file; filed as its own task.
- **`scripts/check.sh` could probably leave `excluded()`.** It was excluded from the name scan
  because it held the allowlisted literal; it no longer holds one. Removing it would make the
  guard scan its own source. Not done here — it widens the change and any future literal would
  then fail the build.
- **Section 6's object counts move with ordinary git work.** A rebase and a stash took this
  store from 28 blobs/32 trees to 34/40 inside one session. That is why the section keys on
  pattern hits and never on counts, and why the baseline holds hashes rather than a total.
- **Running `check.sh` from outside the repo dies silently**, because its own
  `cd "$(dirname "$0")/.."` lands it elsewhere and every later path is wrong. Met while building
  a fixture. The same shape as `ws-refine`'s part 2, which asserts where it is before reading.

**A third fail-open, found by the second review round and the sharpest of them.** A pattern file
yielding a regex `grep` cannot compile silenced sections 1 and 6 **entirely**: one unbalanced
bracket makes grep exit 2 on every file, and the `|| true` on each call swallows it, so both
printed `ok` at exit 0 on a real leak. Reproduced with a single plausible typo in an existing
line. The section 1 half **predates this task** — and this task is what made it dangerous, by
deliberately routing all coverage through that one file. The patterns are now compiled once
against empty input before anything is read. Dismissing it as pre-existing was the obvious move
and the wrong one.

Three narrower gaps came with it, all measured: NUL bytes truncated the line before the patterns
saw it, and BSD grep skips binary input anyway, so both halves of the pipeline missed a name
after a NUL — pre-existing, and newly important because section 6 points this scan at arbitrary
object-store blobs, where a staged image from a refused commit is exactly the residue it exists
for. `git ls-tree --name-only` C-quotes a non-ASCII name, so `café-<name>` was read as its
escapes. And `disable-model-invocation: True` is true in YAML 1.1 and was reported as the flag
being absent.

**The withdrawn finding, and why it was withdrawn properly.** The first round's most alarming
claim was that a blob left by a refused commit is `dangling` rather than `unreachable`, so
section 6 missed its headline case. It did not reproduce here, four ways. Rather than being
waved away it went back with the measurements, and the reviewer found its own cause: its fixture
repo had no commit and therefore no refs, and `git fsck --unreachable` reports a loose object as
`dangling` with no default references and as `unreachable` once one ref exists. Same blob, same
flag, two answers. The `notice: No default references` line was in its own transcript.
