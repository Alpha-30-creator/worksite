## p1.2 — Prove the leak guard actually refuses a commit · 2026-11-02 · @Alpha-30-creator

**What changed:** one dated record in `docs/records/` measuring the guard refusing a real commit,
plus two standing boundaries in `known-limitations.md` (header `Eleven` → `Thirteen`). **No source
file changed** — the guard was tested, not altered. Two of the task's four criteria had already
been delivered by p4.3 and were ticked on that evidence when the task was re-scoped.

**Decisions:**
- **The false-positive criterion is a test, not a fix.** `LICENSE` is in `check.sh`'s `excluded()`
  and `skills/ws-shared/new-device.md` already carries `@abdur-codes/...` in a tracked,
  non-excluded file with §1 green. Nothing needed changing, and saying so was the deliverable.
- **Rejected: attempting the leaky commit first.** That is circular — it is only safe if the guard
  works. Replaced by running `check.sh --staged` **directly** and attempting the commit only after
  observing exit 1, with an explicit stop-and-escalate if it ever exits 0.
- **Rejected: quoting the private pattern anywhere committed**, the worklog included. The record's
  safety rests on `docs/records/` *not* being in `excluded()`, so a private name there makes
  `check.sh` red and the record uncommittable. Redaction is enforced by the mechanism being
  documented rather than promised, and a green final check is the proof.
- **Rejected: `git gc` to clear the probe's residue.** The object store is shared with live
  worktrees whose unreachable objects are wanted, so the blob was removed by exact hash.
- **Rejected: recording the two measured defects as limitations.** Both became criteria on p8.31
  (`d34ab8c`) instead. Recording something about to be fixed as a standing limitation is wrong,
  and `ws-task`'s first routing row makes a gate that passes without doing its job a task.

**Evidence:** PR #13, CI green in 5s, `check.sh` exit 0 on the working tree, on the staged bytes
via the hook, and after. A1/A2/A3 record the refusal with the `file:line` prefix read from each of
three runs rather than inferred from one; B1 proves `CONTRIBUTING.md`'s documented install yields a
working guard from zero; B2/B3 the false positives in both modes. Two of six invocation sites were
exercised — the three `publish.sh` sites and CI were not, and the record says so rather than
implying coverage.

**Risks learned:** **a refused commit still leaves its content in the object store.** `git add`
writes the blob before the hook can refuse it and `git restore --staged` only rewrites the index.
Recorded as a limitation. Measuring the whole store afterwards found two unreachable blobs carrying
private project names *inside a packfile*, predating this task — residue of the P2
depersonalisation. `origin/main` is clean and unreachable objects are never pushed, so nothing
escaped; the owner's decision was to leave them and keep the assertion as a p8.31 criterion
(`520e2cf`), since pruning safely needs the live worktrees gone first.

**A lesson about reviewing, not about the guard:** the independent review filed two Must-fixes
saying the record cited p8.31 criteria that do not exist. It quoted p8.31 accurately and grepped
the whole roadmap to confirm — and was reading a branch cut *before* the tracker edit. Both
criteria were on `main`. The cause was the lead's brief omitting that the tracker had moved, the
second instance of that same omission in this project. Every later brief in the batch named the
tracker commits. The record now cites `d34ab8c` so the claim resolves from any branch, which is the
durable half of the fix.
