## p3.5 — Stale pointers and the skill count in the cartridge · 2026-11-02 · @Alpha-30-creator

**What changed:** nine edits to `docs/agent/reference.md`, the project cartridge — the first file any
agent reads before working here. Filed as three fixes; nine were needed.

**Decisions:**
- **The scope was wrong in the filing, and the gap is the finding.** Four of the nine were found on a
  full re-read rather than at the named sites. Cause: the cartridge was **frozen for an entire
  previous batch** while five tasks shipped around it, and nothing owns keeping it current — so the
  file every agent reads first became the most out-of-date file in the repo. *Rejected:* filing the
  four extra as a separate task; same defect, same file, one reading.
- **The dead open question was deleted, not rewritten.** It said "p2.1 — who owns the skills?
  Blocking the whole of P2. Needs an ADR", and p2.1 was decided by ADR 0001. A reader starting here
  concluded P2 was blocked on a settled question. The decision's home is the ADR; rule 2 now carries
  the conclusion with the link, so nothing was lost. *Rejected:* keeping it "for history" — that is
  how a stale file stays stale.
- **Thirteen skills plus `ws-shared`, with the reason attached** so the next reader does not flip it
  back: `skills/` holds fourteen directories, `ws-shared` is reference material rather than a loop
  step, and it carries `disable-model-invocation: true` deliberately (p8.1).
- *Rejected:* a **"last reviewed" date** on the cartridge. It would have caught all nine, but a date
  is a claim nobody enforces, which is the pack's own argument against anything depending on memory.
  The real fix is `ws-ship` refreshing the cartridge rows a shipped task invalidates — filed, not
  smuggled in here.
- **The ADRs are now linked where task ids used to point.** The cartridge cited no ADR before this
  change; it cites 0001 twice and 0002 once. A cartridge that links decisions goes stale more slowly
  than one that names task ids, because a closed task survives only as long as its roadmap entry.

**Evidence:** PR #4. `bash scripts/check.sh` green on the working tree, the staged tree, and via the
pre-commit hook. The skill count was cross-checked by grep against `README.md` and
`product/overview.md` — all three now agree, and "fourteen" appears only as the directory count the
text reconciles. The publish row was read for reconstructability rather than trusted to the scan: no
path, no config filename, nothing from which the destination could be rebuilt.

**Risks learned:** two, one of them transferable beyond this repo.
- **"Is this still true?" is not the only staleness test.** Tense and completeness go stale while
  every clause stays technically accurate — the worklog row described an empty directory holding
  eight files, and the `docs/` row read as a closed inventory that omitted two directories. Both got
  past a deliberate full re-read looking for false statements. The test wants to be "does this row
  still read correctly", not just "is it still accurate".
- **A doc can attribute a configuration-driven path to the wrong half of a mechanism**, and the leak
  guard will never catch it: the guard looks for leaked names, not for true-sounding claims about
  which component holds the private path. This was the review's must-fix, and it **originated in
  this task's own plan** rather than in the edit — the plan's sentence was true of the target list
  `ws-refine` iterates and false of `publish.sh`'s destination.
