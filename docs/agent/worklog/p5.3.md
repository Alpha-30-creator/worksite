## p5.3 — `ws-env init`, and the services the agent must drive · 2026-11-04 · @Alpha-30-creator

**What changed:** `ws-env` gained a fifth mode, `init`, which creates an encrypted credential store
from nothing — the other four all assumed one existed, and its own pre-flight told a first-ever
machine to clone a store it does not have. `ws-setup`'s question 13 now also asks **which managed
services the agent itself must drive**; the user names them, the agent researches each from its own
current documentation, and concludes *how* access works from a closed vocabulary of four kinds. A
credential file is written only where one is needed, at `<state_dir>/env/agents.env`, with every
value empty. `ws-sync` gained step 3b, which re-runs each service's read-only check on the machine
it is run on. Two cartridge keys (`services:`, `agent_env:`) plus `env_file:`; ADR 0007.

**Decisions:**
- **The pack names no service, and `access:` is a conclusion rather than a question.** Rejected: a
  table of named services shipped in the pack, which was this task's own first design and the
  owner's first correction. Two independent faults — it scopes a project to whatever is in the
  table, and it assumed every service needs a pasted credential. The second is **falsified by the
  author's own machine**: two of his projects reach their host through a CLI he signed in once, and
  no credential for it exists anywhere. The generic thing is the *shape* of access, not the service:
  `cli-session`, `token`, `runtime-var`, `none`.
- **`access: none` is an answer, not a gap.** It is what makes an agent ask for a deploy instead of
  hunting for a way to do it itself, and step 3b will not run a check against such a service even
  when one is recorded.
- **Rejected: the agent obtaining credentials itself**, through a service's login or OAuth flow.
  That puts the pack inside an authentication boundary it has no business in, and an agent entering
  a credential on a human's behalf is prohibited rather than discouraged. The human runs `login`;
  the pack prints the command. Reinforced by measurement: an interactive login **blocked
  indefinitely** when a check ran it, which is why every check now closes stdin and is time-bounded.
- **Rejected: keeping the credentials only in the encrypted store**, with nothing declaring what
  exists. The store answers "what do I have"; it cannot answer "what does this project need, and do
  I have it *here*" — and that second question is the whole point, because a signed-in CLI is signed
  in on exactly one machine.
- **Rejected: dropping the printed command output** to stop a credential leaking into the report.
  The last line of a check is the most useful thing in the row, so it is scrubbed instead.
- **Where files live follows the author's own convention**, read from a live workspace rather than
  designed: `<state_dir>/env/`, not the state dir root, *so that the routine habit of reading
  `<state_dir>/*.md` never touches a secret*; one `agents.env` holding only the agent's own
  credentials; a generated `README.md` beside it carrying the where-it-goes table, the loading line
  and which side is the source of truth.
- **The schema keys landed inside section 9 rather than as a new section 10**, because two worklog
  entries cite later section numbers and `records/` is immutable in substance.

**Evidence:** execution, not reading. `init`'s block was extracted verbatim and run against
throwaway stores: the tool-missing refusal with nothing written, the existing-store refusal,
`--repair` keeping `.sops.yaml` and a manifest row while restoring a deleted hook, the hook refusing
a plaintext commit with the initial commit intact, and a full sops round trip byte-identical back
into a throwaway workspace, compared by hash with no value printed. Step 3b was run against eleven
fixtures covering all eight outcomes and five cartridge shapes that must not be parsed — including
this repo's own `services: []`. `bash scripts/check.sh` 7/7; the graph audit at its one pre-existing
finding. Not proved, and recorded as such: that a stranger finds question 13 clear, and that `pull`
round-trips on a second machine.

**Risks learned:** four review rounds, each of which found defects **created by the previous
round's fixes** — twelve, ten, ten, ten, a count that never fell. The five worth keeping:
1. **A guard that is written but not switched on.** Git silently ignores a non-executable hook and
   commits anyway; the closing line would have said `hook installed`.
2. **A secret is not a regex.** Interpolating a credential's value into a `sed` expression leaked it
   three ways — `|` or `[` in the value made sed print the value in its own error message, a
   backslash made it silently fail to match itself, and `a*b` matched the bare `b`. And scrubbing
   *after* truncating prints the first 60 characters of a long secret, because a cut value no longer
   matches itself.
3. **An exit status read twice** tests the first `[` the second time, so a timed-out check reported
   as an ordinary failure — on GNU only, which is where CI runs.
4. **A fix bounded one key and not its neighbour**: `agent_env` was read from the frontmatter while
   `services:` was still scanned across the whole file, so a `services:` example in a cartridge's
   prose would have been parsed and its check run.
5. **For anything that will be executed, a fixture is worth more than a review round.** The hang,
   the leak, the truncated secret and the misparse of this repo's own cartridge all came from
   running it against deliberately awkward input, not from reading it.
