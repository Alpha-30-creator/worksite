## p8.13 — `for r in <repos>` survives in three skills, including one that warns against it · 2026-11-03 · Alpha-30-creator

**What changed:** the three remaining `for r in <repos>; do` loops — `ws-start` §1, `ws-plan` §1
and `ws-review`'s one-pass gather — became the heredoc `while IFS= read -r r` form that
`ws-shared/tracks.md`'s retirement block has used since p8.10, each with the reason written beside
it. `ws-review`'s block also had bare `git -C $r` at five uses and an inner `while read -r f`; both
are now quoted, and its `cd "<workspace>"` moved inside a subshell with `|| exit 1`. Every loop
gained a `git -C "$r" rev-parse --show-prefix` guard and a quoted `<<'REPOS'` delimiter — including
`ws-start`'s orphan-worktree sweep, which the acceptance criteria did not name but which has the
same shape in the same file. `ws-shared/reference.md`'s cross-platform table gained the mirror
image of its zsh row. `ws-plan`'s `What next?` now lists `ws-start` and `ws-start`'s lists
`ws-setup`, closing the two unlisted exits p8.24's reverse check reported.

**Decisions:**
- *Rejected: quoting the `for` list* (`for r in "$a" "$b"`). Correct, and the smaller diff.
  Rejected because the template `for r in <repos>` has nowhere to put the quotes, so the next agent
  fills it bare. The shape has to be hard to fill wrongly, not merely possible to fill rightly.
  **Note the precise claim** — a `for` list *can* be quoted; `ws-sync`'s is. The first draft of
  `known-limitations.md` over-reached and said otherwise, and review caught it.
- *Rejected: one shared snippet file the three skills link to.* A delivered skill body must stand
  alone; an agent that does not open the link gets no loop at all.
- *Rejected: a counter plus a non-zero exit when every path is refused.* More code in a block an
  agent pastes, for a signal the output already carries unmissably. Recorded as a limitation: the
  guard is loud but not fatal, so the output is what to read.
- *Rejected: tightening the guard with `--is-inside-git-dir`.* `--show-prefix` is empty inside the
  git directory too, so `<repo>/.git` passes — but it then fails loudly at `git status`, and nobody
  fills a repo list with `.git`. Recorded rather than coded.
- *Rejected: leaving the heredoc delimiter unquoted* with the rationale that quoting would break
  `tracks.md`'s `$repos` fill. That rationale was simply false — different blocks, different file.
  The skills' heredocs hold literal paths and are now quoted; `tracks.md`'s loops stay unquoted
  because theirs must expand. Both correct, and the asymmetry is now written down.
- *Deliberately not changed:* `ws-sync`'s `for p in $(projects)` and `for r in "$root" "$root"/*/`.
  The first is safe because the `sed` producing the ids constrains them to `[a-z0-9-]`; the second
  is glob-based and quoted. Both look like the bug and neither is one.

**Evidence:** [PR #20](https://github.com/Alpha-30-creator/worksite/pull/20), merged `c651e12`;
library `7e2b84d`; published `4f5e6d1`. All four loops extracted from the **delivered** copy in
`~/.claude/skills/` rather than retyped, and executed under `bash` against a fixture at
`<scratch>/My Projects/` holding two repos, a plain subdirectory and a linked worktree. Before: four
path fragments per loop instead of two repos, every `git -C` fatal, a row printed per fragment,
exit 0. After: two real repos, the dirty diff shown, a spaced filename read, the sweep printing its
one worktree id. Plus twelve fillings run before and after the guard with the raw output of all 24
runs kept. Audit: 45/45 under all three agents, 0 broken links, 0 positional parameters, unlisted
exits 3 → 1. `bash scripts/check.sh`: all six sections, on the branch, on the staged tree and on
the published target.

**Risks learned:**

*A fix for a reports-success defect can reproduce it inside its own template.* Round one found that
the corrected loop still printed a reassuring row at exit 0 whenever the **fill** was wrong — worst
case the placeholder left in verbatim, printing `<repo paths, one per line>   0 changed`. Round two
then found the guard added for that had the same flaw in miniature: `rev-parse --git-dir` succeeds
inside a repo by discovery, so a *subdirectory* was accepted and git reported on the parent, with
no error printed anywhere. **Second occurrence of this shape in two tasks** — p8.24 reproduced its
own defect class three times. The generalisation now worth carrying: after fixing a check that
passed on empty input, ask what its *replacement* does on malformed input, because the new code
inherits the audience's trust without inheriting the scrutiny.

*The audit's unlisted-exit output is now a baseline rather than noise.* Exactly one finding remains,
`ws-ship`'s "as `ws-review` does", which the 2026-11-02 record's own table already marks a false
positive. Any second finding is new. A reported-but-accepted false positive turns a low-precision
check into a tripwire, the same way `scripts/object-store-baseline.txt` did for §6.

*The over-claiming moved from prose into the evidence, which is worse.* Review found three false
documentation statements, two mislabelled evidence files and six evidence claims that said more
than the file they cited — including a matrix row that misread the raw output printed directly
beneath it, and a file labelled "SHIPPED blocks" that held the pre-guard ones. Prose a reviewer
will re-derive; evidence is what a reviewer trusts *instead of* re-deriving. Both files were
regenerated from the delivered copy with their driver script kept beside them, the superseded one
renamed rather than deleted, and the track's `00-criteria.md` records which rows were rewritten and
why. Third task running with this defect class (p8.31: five, p8.37: five), and the first where it
reached the artefacts rather than the commentary.

*A reviewer that dies mid-run still delivers, if its brief demanded a log.* Round one's shell
reviewer was killed by an API classifier error. Its continuously-appended log had already captured
almost its whole scope, including the filling matrix that found the most important defect in this
track. The brief requirement that produced that log came from p8.24's harvest; this is the first
time it paid.
