## p8.39 — `git -C <repo>` is unquoted in the pack's placeholder idiom · 2026-11-03 · @Alpha-30-creator

**What changed:** every single-path placeholder inside a runnable fenced command in the `ws-*` pack
now carries its quotes — about thirty `git -C "<repo>"` sites across ten of the fourteen skills,
plus the two **assignments** in *Retiring a track*, the suppressed reads in `ws-start` and
`ws-task`, `cd "<repo>"`, `cat "<docs>/…"`, `sops -d "personal/<file>"`, the `trello` eval
redirect, `--body-file "<body>"`, and `git clone … ~/"<folder>"`. The nine **prose** sites that
*teach* the idiom were quoted too, including `ws-setup`'s two templates, which are generated into
every new workspace and were therefore teaching the broken form in the authoritative sentence. A
third row joins p8.13's two word-splitting rows in `ws-shared/reference.md`'s cross-platform table.

**Decisions:**
- **Quotes in the template, not a note beside it.** The criterion allowed either. p8.13's lesson
  rules out the note: a template must be correct when filled *naively*, because the naive fill is
  what an agent produces, and a rule with no path that enforces it is the shape p7.3 had just
  closed on this repo's own front page.
- **A stated not-to-quote set**, because an agent told "quote the path placeholders" will quote
  these too and each one breaks: `<paths…>` is several words on purpose; `-R <owner>/<repo>` is a
  GitHub slug; a **bare id** cannot hold a space. An id composed *into* a path is a path and takes
  the quotes. *Rejected:* quoting uniformly.
- **Two forms that look wrong and are right:** `~/"<folder>"`, because a tilde does not expand
  inside quotes, and `"<path>"/P*.md`, because the glob must stay outside them.
- **The assignments first.** Every *use* in the retirement block was already `"$state_dir/…"`; the
  assignment was the one place the value was unprotected, and it is where the failure is born.

**Evidence:** four artefacts in the track's `verify/` — the before/after inventory, the table, the
execution proof against a fixture at `<base>/My Projects/`, and the graph audit. A reviewer
independently reproduced all five shapes with the same results, enumerated 253 fenced placeholders
across all fourteen library skills, and found exactly one site missed (`--body-file <body>`, since
fixed). `bash scripts/check.sh`: all seven sections. `ws-refine/audit.sh`: exit 0, 14 skills,
0 frontmatter / 0 missing / 0 broken link findings.

**Risks learned:**
- **The task was filed with the wrong severity, and the wrong severity is why it was deferred.**
  The body said it "fails loudly … so it wastes a run rather than lying about one", and that was
  the stated reason not to fix it inside p8.36. Measured: of five shapes, three are silent and one
  is loud and *then* falsely reassuring. `git -C <repo> status --porcelain` inside `$( )` prints
  `0 changed` at exit 0. The `2>/dev/null` that exists for "the file is absent" suppresses "you
  split my path" identically, so `ws-start` reads *no current track* and *no tracks on this
  machine*. And an unquoted **assignment** does not split at all: bash reads
  `state_dir=/x/My Projects/.p` as a prefix assignment for the command `Projects/.p`, which fails
  and does not persist, leaving the variable **empty** — so `rm -rf "$state_dir/tracks/$id"` is
  `rm -rf "/tracks/$id"` at the filesystem root, exits 0, and the verification beside it checks the
  same wrong path and prints `clean: track removed` over an intact track. **The block guards the
  `id` against precisely this and never guards the `state_dir`**, which reaches the same place by
  another route.
- **My correction of that severity claim was itself false, twice.** It said four of five were
  silent — the assignment prints an error and exits 127, which my own evidence file captured
  directly beneath a heading calling it silent. And it credited the empty-variable path with
  destroying an unrelated file at the first fragment; that cannot happen, because with the variable
  empty `rm` receives **one** argument. The destruction was measured on a different shape, an
  unquoted *use*, and **no `rm` in the pack has that form**. Both went into the public task body
  and the README before review caught them. Tenth and eleventh instances on this project of a
  false statement written while fixing a false statement.
- **Three further shapes were fixed that the five do not count**, two genuinely silent:
  `printf … > <state_dir>/tracks/current` exits 0 having written into a file named `My` while
  `tracks/current` is never created; `mkdir -p <state_dir>/tracks/"$id"/verify` exits 0 having
  built a wrong tree; and `cd <repo> && npm …` exits **0 in the first fragment**, because bash's
  `cd` silently ignores extra arguments — so a project's own checks run in the wrong directory and
  report normally. That last one is the most alarming of the set and was found by review, not by me.
- **The leak guard earned its keep.** My first draft of the corrected task body named a private
  project in order to show that real workspace paths contain spaces. Section 1 refused it in the
  working tree, before the commit, which is exactly the rule in `AGENTS.md`.
- **A permanent record must not cite an ephemeral one.** An earlier draft of the limitations entry
  pointed a reader at this track's `verify/01-inventory.txt`, which is gitignored and is deleted
  when the track is retired. The not-a-command list lives here instead.
- **Not hypothetical.** Three of the five workspace paths in the author's `device.yaml` contain a
  space, and so does the path this repo is developed at — so every `git -C <repo>` an agent filled
  in for *this* project would have split.
- **Pre-existing, found by the audit and left as a line rather than filed:** `ws-ship`'s prose
  mentions `ws-review` twice (as what it *does*, not as somewhere to go next) while its
  `What next?` list does not name it. The published copy has the identical condition, so it
  predates this task. A wording defect, which *Where a finding belongs* routes here, not to a row.

**Fenced blocks deliberately left alone, because they are not commands.** Named so the silence is
not a gap a later reader has to re-derive: `ws-setup/SKILL.md` (a generated-by header and three
table rows); `ws-shared/reference.md` (a directory tree, two risk-file paths in a listing);
`ws-shared/tracks.md` (a directory tree, a worklog field, a config sample); `ws-ship/SKILL.md`
(two printed lines, a worklog field); `ws-start/SKILL.md` (an `awk -v` value, a comment, three
table rows, the `task.md` Worktrees line); `ws-sync/SKILL.md` (a comment, a generated-by header);
`ws-shared/new-device.md` (`mkdir -p .<project>/tracks` — a bare id, which cannot hold a space).
