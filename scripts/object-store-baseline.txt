# Unreachable objects that are KNOWN to carry a pattern from scripts/leak-patterns.txt.
#
# Section 6 of scripts/check.sh reads the unreachable objects in .git/objects and fails on any
# that carries a pattern and is not listed here. It reads BOTH kinds: a blob's content, and a
# tree's entry names — a path like src/<private-project>/ leaks the same string with perfectly
# clean file content. Unreachable COMMIT objects are not read, because every commit header
# carries the committer's name and email, so a pattern list holding the author's name matches
# all of them; section 6 prints how many it skipped rather than implying it read them. This file is a declaration, not a suppression:
# every hash below was measured, identified and decided about on the date in its row, and a hash
# that is not here fails the check.
#
# Why any of this exists: `git add` writes a blob before a pre-commit hook can refuse the
# commit, so a commit the guard REFUSED still leaves its content in the object store. Sections
# 1 to 5 read the working tree or the index and never looked there.
#
# Nothing here has escaped. Unreachable objects are never pushed, and every file in the pushed
# tree of origin/main was checked against the full pattern set with the allowlist applied and is
# clean. These are local residue on one machine; a fresh clone holds none of them, and there
# section 6 reads zero unreachable objects and says so.
#
# ---------------------------------------------------------------------------------------------
# THE DECISION, 2026-11-02: leave them. Do not prune.
#
# The obvious remedy is `git gc --prune=now`, and it is the wrong one here. This workspace's
# object store is SHARED with the live worktrees under ../worksite-tracks/, whose unreachable
# objects are wanted — a prune would destroy work in progress that is not residue at all. The
# residue is harmless where it sits (nothing pushes it), it is now asserted rather than
# unknown, and the cost of removing it safely is higher than the risk it carries. Revisit only
# when no worktree is live, and then by the procedure in
# docs/runbooks/purge-a-leak-from-history.md rather than by a bare prune.
# ---------------------------------------------------------------------------------------------
#
# Format: <40-hex sha> <blob|tree> <date measured> <what it is, generically>
#
# The kind is recorded because the two are different declarations: a blob row forgives CONTENT,
# a tree row forgives a FILENAME, and the same sha shape means both. Section 6 keys only on the
# sha — the kind is for the person reading this file, which is the whole purpose of declaring
# rather than suppressing.
#
# Measured 2026-11-02 while building p8.31, re-checked 2026-11-03 after the section grew its
# tree scan. Three of the 28 unreachable blobs carry a pattern; none of the 33 unreachable trees
# does, so there is no tree row below. The two further blobs a naive scan reports are matches on
# the allowlisted npm scope alone and are not leaks — which is itself the first evidence that
# stripping the allowlisted substring behaves differently from dropping the line.
#
# Those counts move with ordinary git work: a rebase and a stash took this store from 28 blobs
# and 32 trees to 34 and 40 inside one session. That is why section 6 keys on pattern hits and
# never on a total, and why this file holds hashes rather than a count.
#

# this same task's alias criterion exists to close, found as residue rather than reasoned about.
